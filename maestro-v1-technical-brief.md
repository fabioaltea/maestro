# Maestro V1 — Technical Brief

> Handoff document for implementation. Read this entirely before writing any code.
> The audience is a coding agent (Claude Code) that will scaffold and implement the V1 of Maestro.

---

## 1. What Maestro is

Maestro is a **local CLI orchestrator for AI agents that build software collaboratively**. The user describes what they want to build; an Architect agent leads them through structured discovery (functional → technical → design → planning → staffing); then specialized Engineer agents execute the resulting backlog of tasks on the codebase.

It is positioned as a **wrapper/orchestrator on top of Claude Code**: if the user already has Claude Code installed and authenticated (with their Pro/Max plan), Maestro reuses that auth and infrastructure for free.

The value proposition vs raw Claude Code:
- Structured planning phase (not just "throw a prompt and see what happens")
- Multi-agent specialization with persistent personas
- Per-agent learning over time (memory)
- Backlog-driven execution with dependencies
- Cross-agent coordination via an Architect router

V1 is **single-machine, single active engineer at a time, no UI** (CLI only with tmux sessions). Future versions add containers, parallelism, remote execution, and a VSCode extension. **Do not implement those now.**

## 2. Core concepts and vocabulary

| Term | Definition |
|------|------------|
| **Project** | A user codebase initialized with `maestro init`. Contains `docs/`, `.agents/`, `.maestro/`. |
| **Agent** | A persona defined by a `.md` file in `.agents/`. Has identity, skills, model preference, tools, and a `## Learnings` section. Two kinds: Architect (built-in, one per project) and Engineer (generated by the Architect, N per project). |
| **Task** | A unit of work in the backlog. Has ID, title, description, assigned agent, status, prerequisites, acceptance criteria. |
| **Session** | A live execution of an agent (tmux session). Created when an agent starts working, destroyed when the agent has no more tasks queued. |
| **Phase** | One of the 5 Architect lifecycle stages (Functional Analysis, Technical Analysis, Architecture Design, Planning & Backlog, Staffing). |
| **Gate** | An explicit user approval point between Architect phases. |

## 6. Auth and LLM backend

Two modes, configurable per-agent:

**Mode A — Claude Code CLI (default).** Maestro spawns `claude` as a subprocess in a tmux session. The user must have Claude Code installed and authenticated. This uses the user's Pro/Max plan (or whatever auth Claude Code is using). Pass system prompt and model via Claude Code flags.

**Mode B — Anthropic SDK direct.** Maestro uses `@anthropic-ai/sdk` directly with `ANTHROPIC_API_KEY` from env or `~/.maestro/config.yaml`. Used when the user explicitly wants API billing or doesn't have Claude Code.

The `LLMProvider` interface abstracts both. The Architect uses **Mode A** by default (via Claude Agent SDK if available, falling back to spawning `claude` headlessly). Engineers use **Mode A** by default.

Resolution order for a given agent's model and mode:
1. Frontmatter of the agent's `.md` file
2. Project config `.maestro/config.yaml`
3. Global config `~/.maestro/config.yaml`
4. Hardcoded default (Sonnet 4.6, Mode A)

## 7. The Architect

### 7.1 Lifecycle (5 phases)

The Architect runs through 5 phases as a state machine. Each phase corresponds to one task pre-populated at init:

| Task ID | Phase | Output | Conversational? |
|---------|-------|--------|-----------------|
| ARCH-001 | Functional Analysis | `docs/01-functional-analysis.md` | Yes (heavy) |
| ARCH-002 | Technical Analysis | `docs/02-technical-analysis.md` | Yes (heavy) |
| ARCH-003 | Architecture Design | `docs/03-architecture.md`, `04-data-model.md`, `05-api-contracts.md` | Mixed (mostly autonomous, asks user on key decisions) |
| ARCH-004 | Planning & Backlog | `docs/06-backlog.md`, `.maestro/backlog.json` (ENG-* tasks added) | Light (review at end) |
| ARCH-005 | Staffing | `.agents/<engineer>.md` files | Light (review at end) |

Prerequisites are linear: ARCH-002 needs ARCH-001 done, etc.

### 7.2 Architect tools

The Architect has the following tools (implemented as MCP-style tool calls):

- `read_doc(path)` — read any file in docs/ or .agents/
- `write_doc(path, content)` — create or overwrite a doc file
- `update_doc(path, section, content)` — patch a section of a doc
- `read_agent(name)` — read an agent .md
- `write_agent(name, content)` — create a new engineer agent
- `update_backlog(operations)` — add/update/remove tasks; ops are typed
- `get_backlog()` — read current backlog
- `request_user_input(question, context?)` — block until user replies via chat
- `set_phase_status(task_id, status, summary)` — mark phase complete, ready for gate
- `notify_failure(task_id, reason)` — used during retry triage

### 7.3 Phase gates

After completing each phase, the Architect:
1. Generates the artifact(s).
2. Calls `set_phase_status(task_id, 'awaiting_approval', summary)`.
3. The system shows the user a summary in the agent's tmux session and waits for explicit approval (user types `approve` or `revise <feedback>`).
4. On approve: task → `done`, next phase task → `ready`, Architect proceeds.
5. On revise: Architect incorporates feedback and re-emits.

The user can also intervene mid-phase by simply typing in the tmux session (see section 10).

### 7.4 Functional Analysis (ARCH-001)

The Architect's job in this phase:
1. Greet the user briefly, explain it will guide discovery.
2. Ask open-ended starter: "Tell me what you want to build and who it's for."
3. Internally maintain a checklist (not shown to user) of required signals:
   - Target users / personas
   - Primary use cases
   - Core value proposition
   - Critical user flows
   - Edge cases the user cares about
   - Compliance / regulatory constraints (if any)
4. Ask follow-ups one or two at a time, never bombarding.
5. **Proactively propose alternatives** when the user is vague or the choice seems suboptimal. Always with rationale and trade-offs.
6. Maintain an **Assumptions** list with IDs (FA-A-1, FA-A-2…). The user can challenge them.
7. When the checklist is sufficiently covered, generate `docs/01-functional-analysis.md` and call the gate.

### 7.5 Technical Analysis (ARCH-002)

Same pattern but checklist is technical:
- Stack preferences / constraints (languages, frameworks)
- Hosting / deployment target
- Auth approach
- Persistence
- External integrations
- Non-functional requirements (perf, scale, security, availability)
- Team that will maintain
- Budget constraints

If the user has already given technical hints in phase 1 (because they pasted a brief), the Architect picks them up and only asks about gaps.

### 7.6 Architecture Design (ARCH-003)

Mostly autonomous. The Architect:
- Drafts architecture (components, boundaries, communication patterns).
- Drafts data model (entities, relationships, key fields).
- Drafts API contracts (endpoints, schemas).
- Calls `request_user_input` only on **key design decisions** with material trade-offs (e.g., monolith vs services, sync vs async, SQL vs NoSQL when not already decided).
- Output is three docs.

### 7.7 Planning & Backlog (ARCH-004)

The Architect decomposes the architecture into tasks:
- Each task has: id (`ENG-NNN`), title, description, acceptance criteria, prerequisites (other task ids), required skills (tags from a controlled vocabulary, see section 9), estimated complexity (S/M/L), area (frontend/backend/data/infra/test/etc.).
- No agent is assigned yet (that's phase 5).
- Updates `.maestro/backlog.json` and emits `docs/06-backlog.md` for human reading.
- Light gate at the end: shows summary, asks for approval.

### 7.8 Staffing (ARCH-005)

The Architect:
1. Loads all `ENG-*` tasks from the backlog.
2. Clusters them by required-skills overlap. Algorithm: greedy — sort tasks by skill set, group consecutive tasks that share ≥70% of their tags.
3. Names each cluster (e.g., `frontend-react`, `backend-fastapi`, `dba-postgres`, `sharepoint-dev`).
4. For each cluster, generates an engineer `.md` file in `.agents/` based on `_base/engineer.md` template, filling sections with cluster-specific content (skills, conventions, tool preferences, etc.).
5. Assigns each task to its corresponding agent (updates `assignee` field in backlog).
6. Picks a default model per agent based on task complexity:
   - Cluster with mostly L tasks or `architect-grade` skills → Opus 4.7
   - Cluster with mostly S tasks → Haiku 4.5
   - Otherwise → Sonnet 4.6
7. Light gate: shows the user the list of generated agents with their model. User can edit `.md` files directly before approving. **No interactive wizard.**

### 7.9 Architect always available

After ARCH-005 completes, the Architect is **not done**. It remains alive as a **router/PM runtime**:
- Other agents can call `request_cross_agent_change(target_area, description, blocking)` → Architect creates a new task, assigns it.
- Engineers signal failures → Architect runs triage (section 8.4).
- User can `maestro chat architect` anytime to: revise plan, add features, do incremental staffing.
- The Architect handles **drift detection**: when an engineer reports a deviation from spec, the Architect reviews and updates the relevant doc.

Implementation: the Architect's tmux session stays alive after ARCH-005 with a long-running event loop waiting for triggers.

### 8.2 Engineer tools

Implemented as MCP tools or as Claude Code's built-in tools (via Claude Code mode):

- `read_file(path)`
- `write_file(path, content)`
- `edit_file(path, old, new)`
- `run_shell(command)` — with approval policy (default: auto-approve for safe commands, prompt for destructive)
- `run_tests(scope?)`
- `git_status()`, `git_diff()`, `git_commit(message)`, `git_checkout(branch)`, `git_create_branch(name)`
- `ask_user(question)` — non-blocking; queued for next user attention
- `request_cross_agent_change(target_area, description, blocking)` — escalates to Architect
- `update_docs(file, changes, deviation_reason?)` — records actual implementation diverging from spec
- `update_learnings(content)` — appends to own `## Learnings` section
- `report_failure(reason, last_state)` — invokes triage

Approval policy is controlled by a config:
```yaml
approvals:
  default: auto              # auto | prompt | gate
  destructive: prompt        # always prompt for rm, drop, force-push, etc.
  network: prompt            # commands that hit the network
```

### 8.3 Engineer execution flow

1. Scheduler picks next ready task assigned to this engineer.
2. Acquires working-tree lock (only one engineer holds it at a time in V1).
3. Creates branch `feature/<task-id>-<slug>` (or checks out existing if resuming).
4. Spawns a tmux session named `agent-<engineer-name>` if not already alive.
5. Inside the session, launches the agent runtime:
   - **Mode A (Claude Code)**: `claude --model <model> --system-prompt-file <path-to-md> --append-system-prompt "<task context>"` (exact flags TBD per Claude Code's actual CLI).
   - **Mode B (SDK)**: Anthropic SDK loop with system prompt = full agent .md + task context.
6. Initial prompt to the agent contains: task description, acceptance criteria, relevant doc excerpts, latest learnings, prerequisite task summaries.
7. Agent loops: think → tool call → observe → repeat.
8. On task completion:
   - Validates acceptance criteria (self-check).
   - Updates docs if implementation deviated.
   - Appends to `## Learnings` if anything noteworthy was learned.
   - Commits.
   - Marks task `done`.
9. Releases lock, scheduler picks next task. If next task is for the same engineer, reuses session (warm context). If different engineer, kills session.

### 8.4 Failure handling

When an engineer cannot complete a task:
1. Calls `report_failure(reason, last_state)`.
2. System writes `.maestro/sessions/<task-id>/failure.md`.
3. Task status → `failed`.
4. **Architect is auto-triggered** with the failure report.
5. Architect triage:
   - Reads failure report.
   - Decides: **auto-retry possible** (clear missing context, fix is in scope) or **needs user**.
   - If auto-retry: Architect adds context to the task description (e.g., updated schema, missing dependency info), sets task back to `ready`, scheduler re-runs.
   - If needs user: task → `blocked-needs-user`, Architect writes a question, user responds via chat.
6. Maximum 3 auto-retries before forcing user intervention.

### 8.5 Cross-agent coordination

Engineers never directly call other engineers. Always through Architect:

```
Engineer A: request_cross_agent_change(
  target_area: "backend-api",
  description: "Need POST /users/{id}/avatar endpoint accepting multipart, returning URL",
  blocking: true
)
   ↓
Architect:
  - Validates the request (scope, legitimacy)
  - Creates new task ENG-NNN assigned to backend-fastapi engineer
  - Sets prerequisite: Engineer A's current task depends on this new task
  - Engineer A's task → blocked
   ↓
Scheduler picks new task → backend-fastapi works
   ↓
Backend completes → Architect notifies → Engineer A's task back to ready
```

## 10. Sessions, tmux, and user interaction

### 10.1 Session model

- One tmux session per active agent: `agent-<name>`.
- Created when agent starts a task, kept alive while agent has queued tasks, destroyed when idle.
- All agent output (reasoning, tool calls, results) flows to stdout in the session.
- A structured event stream is also emitted in parallel to `events.log` and SQLite.

### 10.2 Unified `chat` UX

Single command, observer-or-interactive based on user behavior:

```
maestro chat <agent>
```

1. Attaches the user's terminal to the agent's tmux session (`tmux attach -t agent-<name>`).
2. User sees live output: the agent is working, content streams.
3. **As long as the user types nothing**, they are pure observers. Agent doesn't even know they're attached.
4. **As soon as the user types and presses Enter**, the orchestrator detects the input via stdin polling on the agent's process. Agent receives a "user input pending" signal. Agent finishes the current atomic action (current tool call, current LLM response chunk), then enters `paused-for-user`.
5. Terminal shows a chat prompt (`you ›`). User writes their message.
6. User exits chat with `/resume` or Ctrl-D. Agent resumes with the conversation appended to its context.
7. User detaches from tmux with standard `Ctrl-b d` or `/detach`.

### 10.3 `run` UX

```
maestro run                # picks next ready task
maestro run <task-id>      # specific task
```

1. Validates prerequisites.
2. Creates session if needed, starts agent.
3. Auto-attaches user to the agent's session immediately (same as `chat`).
4. If the task is conversational (e.g., ARCH-001), the agent greets immediately and waits for input.
5. If autonomous, the agent starts working and the user observes.

### 10.4 Input detection implementation

Agents are launched as subprocesses within tmux. Their stdin is connected to the tmux pane. When the user attaches and types, characters arrive at the agent's stdin.

The agent's main loop must be non-blocking on stdin:
- Use a separate thread/async reader that fills a buffer.
- Between atomic actions (each tool call, each LLM completion), check the buffer.
- If non-empty, switch to `awaiting-user` state, prompt the user, wait for full input (until Enter), then incorporate into next LLM call.

For Claude Code-based engineers, this is partially handled by Claude Code itself (it has interactive input). Maestro just needs to make sure the user's input reaches the right session.

### 10.5 Pause atomicity

Pauses happen between tool calls, not in the middle. If the agent is in a long-running shell command, the pause waits for that command to complete (or the user can kill the agent with `maestro stop`).

## 11. Backlog and scheduler

### 11.1 backlog.json schema

```typescript
type TaskStatus =
  | 'pending'              // exists, prereqs not met
  | 'ready'                // prereqs met, can be started
  | 'in_progress'          // agent is working on it
  | 'awaiting_approval'    // architect phase, waiting for user gate
  | 'blocked'              // in_progress but waiting (cross-agent or other)
  | 'blocked_needs_user'   // explicit user input needed
  | 'failed'               // failed, in retry triage
  | 'done';

type Task = {
  id: string;                        // ARCH-NNN or ENG-NNN
  title: string;
  description: string;
  assignee: string;                  // agent name
  status: TaskStatus;
  prerequisites: string[];           // task ids
  acceptance_criteria: string[];
  required_skills: string[];         // skill tags
  area: string;                      // frontend | backend | data | infra | test | docs | meta
  complexity: 'S' | 'M' | 'L';
  created_at: string;
  updated_at: string;
  started_at?: string;
  completed_at?: string;
  retry_count: number;
  parent_task?: string;              // if created via cross-agent escalation
  metadata: Record<string, unknown>;
};

type Backlog = {
  version: string;                   // schema version
  project_name: string;
  tasks: Task[];
};
```

### 11.2 Scheduler logic

On every tick (event-driven, not polling):
1. For each `pending` task: if all prerequisites are `done`, promote to `ready`.
2. When a slot is free (no engineer holding the working-tree lock):
   - Among `ready` tasks, pick the one with: oldest, then highest priority, then most dependents (tasks blocked by it).
   - Acquire lock for its assignee.
   - Start agent on the task.
3. Architect is exempt from the lock (it doesn't touch code).

```json
{
  "version": "0.1.0",
  "project_name": "<from cwd>",
  "tasks": [
    {
      "id": "ARCH-001",
```

## 12. Memory and learnings

### 12.1 How learnings are added

After completing a task, each engineer self-evaluates and decides whether to record a learning. Triggers:
- **Made a mistake that was corrected**: e.g., test failed, then fix worked.
- **Discovered a project-specific convention**: e.g., "this project uses X instead of Y".
- **NOT for routine successes.**

The agent calls `update_learnings(content)`:

```markdown
### YYYY-MM-DD — Task #ID (short title)
What went wrong / what I learned. Concrete and actionable.
```

System appends this entry to the agent's `## Learnings` section atomically (file lock, append, save).

### 12.2 Reading learnings

Every time an agent starts a task, it loads its full `.md` (including Learnings) as part of the system prompt. This is how memory persists.

### 12.3 Compaction

When `## Learnings` exceeds N entries (default 30) or M characters (default 8000), a "memory compaction" job runs:
1. Spawn a one-shot LLM call (same model as the agent, or a cheaper one) with: "Here are 30 learnings. Consolidate them into general rules. Output: a concise rules section + the original entries with consolidated tags."
2. Move original entries to `.agents/_archive/<agent-name>-<timestamp>.md`.
3. Replace `## Learnings` content with the consolidated version.
4. Commit (the user sees the diff in git).

### 12.4 Promotion to conventions

If a learning is fundamental and applies project-wide, the agent (or Architect during a review) can promote it to `_base/conventions.md`. This is just a file edit committed to git.

## 14. Cost tracking

For each LLM call, record in SQLite:
- task_id
- agent_name
- model
- input_tokens
- output_tokens
- cached_tokens (if available)
- estimated_cost_usd
- timestamp

## 15. Logging

### 15.1 events.log

JSONL, one event per line. Schema:

```typescript
type Event = {
  timestamp: string;             // ISO
  type: EventType;
  agent?: string;
  task_id?: string;
  data: Record<string, unknown>;
};

type EventType =
  | 'task.created' | 'task.started' | 'task.completed' | 'task.failed'
  | 'task.blocked' | 'task.unblocked' | 'task.status_changed'
  | 'agent.spawned' | 'agent.killed' | 'agent.idle' | 'agent.busy'
  | 'agent.waiting_user' | 'agent.user_input'
  | 'tool.called' | 'tool.completed' | 'tool.failed'
  | 'llm.call_started' | 'llm.call_completed'
  | 'phase.completed' | 'phase.gate_opened' | 'phase.gate_approved' | 'phase.gate_revised'
  | 'cross_agent.requested' | 'cross_agent.completed'
  | 'docs.updated' | 'learnings.appended';
```

### 15.2 Per-task session logs

`.maestro/sessions/<task-id>/`:
- `transcript.log` — human-readable log of what happened
- `llm-calls/<timestamp>.json` — full LLM request/response (system, messages, tools, response, tokens)
- `failure.md` — only if task failed

`maestro logs <task-id>` reads and pretty-prints these.

### 15.3 Future hook for Langfuse / OTel

The event bus is already structured. In V2, add an OTel exporter and a Langfuse adapter as additional consumers. **Do not implement now.**

## 19. Implementation order suggestion

Implement in this order to avoid going off the rails:

1. **Skeleton**: `npm init`, TypeScript config, CLI entry, `commander` setup, `maestro --version`/`--help`.
2. **Schemas**: zod schemas for `backlog.json`, agent frontmatter, events, config.
3. **State store**: SQLite with `better-sqlite3`, basic tables (tasks, events, llm_calls).
4. **Markdown utilities**: parse frontmatter, append to section atomically.
5. **Templates**: write the actual `templates/architect.md`, `_base/engineer.md`, `_base/conventions.md`, `_base/tools.md` files.
6. **`maestro init`**: full implementation. Should produce a runnable project structure end-to-end. Test by running it in an empty dir and inspecting output.
7. **Event bus + status command**: emit events, read events for status display.
8. **Backlog command**: read `backlog.json`, render nicely.
9. **LLMProvider interface + Anthropic SDK provider**: minimal, just send a message and get a response.
10. **Architect runner — phase 1 only (ARCH-001)**: `maestro run` starts a tmux session, runs the Architect through Functional Analysis end-to-end. This is the first real integration test.
11. **Tmux session manager**: spawn, attach, kill, detect input.
12. **`chat` command**: attach to existing session.
13. **Architect phases 2–5**: complete the lifecycle.
14. **Engineer runner via Claude Code**: spawn `claude` CLI, system prompt from `.md`, run a task.
15. **Scheduler**: prereqs, ready promotion, lock.
16. **Cross-agent escalation**: tool + Architect routing.
17. **Failure handling + retry triage**: `report_failure` flow.
18. **Learnings append + compaction**: full memory cycle.
19. **Cost tracking + `cost` command**.
20. **Logs command + session logs**.
21. **Stop, agents, agent, docs commands**: housekeeping CLI.
22. **End-to-end test**: empty repo → init → run through all 5 Architect phases → run a couple of engineer tasks → verify learnings appended → verify docs in sync.
